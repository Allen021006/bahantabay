# AI Usage — Bahantabay

> This document records how AI tools were used while developing Bahantabay and distinguishes AI-assisted work from code and decisions I worked on more independently.

## Documentation note

Bahantabay development began before the `AI-USAGE.md` requirement was introduced to the class.

Because of that, the first entries below are retrospective records reconstructed from the project's Git history, development notes, and my recollection of how each part was developed. I have linked them to the commits that contain the corresponding work instead of presenting them as notes that were written at the time.

Starting with this file, I will update `AI-USAGE.md` alongside the remaining development work so that later entries are recorded during development rather than reconstructed afterward.

I use AI as a development assistant, but the amount of assistance has varied considerably between features. Some parts were primarily generated by AI and then reviewed and tested by me. Other parts were areas I deliberately studied and implemented more independently while still using AI for explanations, review, or troubleshooting.

# 1. How I Used AI

## Entry 1 — Project scope, architecture, and early planning

**Date:** Before and during the early Bahantabay development period  
**Tools:** ChatGPT and Claude

### What I asked AI to help with

I used ChatGPT mainly for general project decisions such as the application flow, framework choices, feature scope, development phases, and deciding what should and should not be part of the MVP.

Claude was also used during proposal and architecture work. It helped me review whether the original project scope was realistic for a student final project and helped identify technical risks involving authentication, database integration, and Supabase Row Level Security.

### What AI returned

The AI tools suggested a smaller Flutter-based MVP with a limited number of screens and a backend architecture that would be manageable within the semester.

Claude also helped compare earlier backend ideas and identify integration risks before implementation.

### What I kept, changed, and why

I kept the general Flutter + Supabase direction because it provided the authentication and database features the project needed without requiring a much larger custom backend.

I did not treat every suggestion as a requirement. Features such as road-following navigation, advanced location controls, and report photos were kept outside the current MVP so that the core flood-monitoring workflow could be completed first.

## Entry 4 — Supabase database schema and Row Level Security

**Date:** September 15, 2026  
**Tool:** Codex

### What I asked AI to help with

This was my first substantial use of Supabase database security in Bahantabay.

I already had experience with relational database concepts through MySQL, but Supabase's authentication integration and Row Level Security model were new to me.

I used Codex as a collaborator to explain the Supabase setup, recommended settings, table structure, authentication relationship, and RLS policies.

### What AI returned

Codex helped produce the initial structure for the `routes` and `flood_reports` tables and their security policies.

It also helped explain how authenticated user IDs could be used to enforce ownership rather than relying only on filtering inside Flutter.

### What I kept, changed, and why

I applied my existing database knowledge while reviewing and editing the proposed database setup so that it matched Bahantabay's requirements.

The final design keeps saved routes private to their owners while allowing flood reports to be publicly readable. Authenticated users can create their own reports, while client-side report update/delete access is not enabled.

I manually applied and tested the database configuration rather than assuming that a generated SQL file meant the security rules were working.

I consider this collaborative/AI-assisted database work rather than completely AI-written or completely independently written work.

# 2. Where AI Got It Wrong

These are cases where AI-generated output was not accepted as correct simply because it was generated. I had to test, identify the problem, and change or request a correction.

## Case 1 — Report Flood responsive form problem

**Tool:** Codex  
**Related commit:** `1bc688d`

### What AI gave me

During the Report Flood implementation, the generated form caused a layout/overflow problem at the phone-sized dimensions used by the application. The dropdown behavior also took more space than expected.

### What was wrong

The implementation could work logically while still producing a poor or broken layout at the actual target screen size.

This mattered because Bahantabay is being designed around a phone-sized interface and the implementation is expected to follow the approved mockups.

### What I did instead

I tested the generated screen at the intended dimensions, identified the layout problem, and had the implementation corrected.

The final dropdown behavior uses the available width more appropriately and removes unnecessary selected-item decoration that contributed to the problem.

### Commit evidence

The corrected implementation is contained in:

https://github.com/Allen021006/bahantabay/commit/1bc688d

The incorrect intermediate version was not committed separately.

### Saved route persistence

**Relevant area:**

`lib/features/routes/`

with related integration in the Home/authentication application flow.

**Primary commit:**

https://github.com/Allen021006/bahantabay/commit/3a913c8

### What I wrote and understand

Route persistence is the existing feature that I chose to study most closely.

Codex helped me get started and explain the required data flow, but I followed the implementation myself, used external tutorials to learn more about persistence, and wrote substantial parts while understanding how the pieces connected.

The flow I focused on was:

1. the authenticated user creates route data;
2. the route service sends the route to Supabase;
3. Supabase stores the route with its owner;
4. Home requests the current user's saved routes;
5. returned rows are converted back into route models;
6. Home refreshes after a successful save;
7. browser refreshes reload persisted data instead of depending on temporary in-memory state.

I also understand why account isolation cannot depend only on Flutter filtering. Supabase RLS provides the database-side ownership boundary, while the application displays the data returned for the authenticated session.

I manually tested this with separate accounts and Guest mode to verify that persistence and isolation worked in the real backend.

Because this phase included both AI guidance and my own implementation, I describe it as my strongest existing self-authored area rather than claiming that every line in the Phase 9 commit was independently written without AI.

# 4. An AI-Written Piece I Understand

## `FloodReportService`

**File:**

`lib/features/flood_reports/data/flood_report_service.dart`

**Commit:**

https://github.com/Allen021006/bahantabay/commit/1bc688d

Codex wrote this service as part of the heavily AI-assisted Phase 10 implementation. I reviewed and tested it rather than writing the file myself.

I chose it for this section because it connects directly to the persistence concepts I have been focusing on.

### What it does

The service is responsible for communication between the Flutter application and the Supabase `flood_reports` table.

Its responsibilities include reading stored public flood reports and submitting new flood reports.

The read side is intentionally different from saved routes. Flood reports are community information, so they can be read publicly, while saved routes are private to their owners.

The write side requires an authenticated user. A submitted report is associated with the current authenticated user while database-generated values such as the permanent row ID and timestamps are returned from Supabase.

### Why it is built this way

Keeping database operations inside a service prevents the UI from directly containing all of the Supabase query logic.

The Report Flood screen can focus on collecting and validating user input, while the service handles persistence.

This also makes the boundary between public report reads and authenticated report creation easier to reason about and test.

RLS remains important even though the Flutter service performs authentication-related checks. Client code should not be treated as the final security boundary because a modified client could bypass Flutter-side restrictions.
