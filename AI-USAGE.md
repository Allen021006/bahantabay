Bahantabay development began before the `AI-USAGE.md` requirement was introduced to the class.

Because of that, the first entries below are retrospective records reconstructed from the project's Git history, development notes, and my recollection of how each part was developed. ### Saved route persistence

**Relevant area:**

`lib/features/routes/`

with related integration in the Home/authentication application flow.

**Primary commit:**

https://github.com/Allen021006/bahantabay/commit/3a913c8

### What I wrote and understand

Route persistence is the existing feature that I chose to study most closely.

Codex helped me get started and explain the required data flow, but I followed the implementation myself, used external tutorials to learn more about persistence, and wrote substantial parts while understanding how the pieces connected.

The flow I focused on was:

1. the authenticated user creates route data;
2. the route service sends the route to Supabase;
3. Supabase stores the route with its owner;
4. Home requests the current user's saved routes;
5. returned rows are converted back into route models;
6. Home refreshes after a successful save;
7. browser refreshes reload persisted data instead of depending on temporary in-memory state.

I also understand why account isolation cannot depend only on Flutter filtering. Supabase RLS provides the database-side ownership boundary, while the application displays the data returned for the authenticated session.

I manually tested this with separate accounts and Guest mode to verify that persistence and isolation worked in the real backend.

Because this phase included both AI guidance and my own implementation, I describe it as one of my strongest existing self-authored areas rather than claiming that every line in the Phase 9 commit was independently written without AI.

# 4. An AI-Written Piece I Understand

## `FloodReportService`

**File:**

`lib/features/flood_reports/data/flood_report_service.dart`

**Commit:**

https://github.com/Allen021006/bahantabay/commit/1bc688d

Codex wrote this service as part of the heavily AI-assisted Phase 10 implementation. I reviewed and tested it rather than writing the file myself.

I chose it for this section because it connects directly to the persistence concepts I have been focusing on.

### What it does

The service is responsible for communication between the Flutter application and the Supabase `flood_reports` table.

Its responsibilities include reading stored public flood reports and submitting new flood reports.

The read side is intentionally different from saved routes. Flood reports are community information, so they can be read publicly, while saved routes are private to their owners.

The write side requires an authenticated user. A submitted report is associated with the current authenticated user while database-generated values such as the permanent row ID and timestamps are returned from Supabase.

### Why it is built this way

Keeping database operations inside a service prevents the UI from directly containing all of the Supabase query logic.

The Report Flood screen can focus on collecting and validating user input, while the service handles persistence.

This also makes the boundary between public report reads and authenticated report creation easier to reason about and test.

RLS remains important even though the Flutter service performs authentication-related checks. Client code should not be treated as the final security boundary because a modified client could bypass Flutter-side restrictions.

## Security pass — flood-report privacy and workflow hardening

**Date:** September 23, 2026

**Tool:** Codex, with my manual repository, Supabase, application, and deployment checks

**Status:** Privacy correction and workflow hardening committed, pushed, and verified as described below. Historical Git author-email exposure remains unresolved.

### Repository and live access audit

I manually checked the repository for passwords, secrets, API keys, tokens, Supabase keys, tracked environment files, and suspicious credential files. The tracked `.env.example` contains placeholders only, and the real `.env` is ignored. `git log --all --full-history -- .env` returned no history, confirming that `.env` was not committed in the checked history.

History searches for `SUPABASE_SECRET_KEY` and `service_role` found documentation/template references rather than actual credential values. No `.env`, `key.properties`, `google-services.json`, service-account JSON, PEM, P12, JKS, or keystore files were found in the checked Git history. I also manually confirmed that GitHub Secret Protection and Push Protection were enabled. These are the results of the checks performed, not a guarantee that every possible disclosure has been ruled out.

In live Supabase, I verified that RLS was enabled for both `routes` and `flood_reports` and inspected the existing policies. My manual app checks confirmed that Guest could read intentionally public flood reports but could not see private saved routes, submit a real flood report, or create a real route. Codex did not perform these live checks.

### What I asked AI to help with

The security review identified unnecessary exposure of `reporter_id`: the client used wildcard SELECT and both anon and authenticated roles could read the internal reporter UUID. This was an ownership-identifier privacy issue, not a password/email leak or an account-takeover issue. Report IDs, locations, timestamps, flood depth, road status, and notes remain intentionally public community data; notes must not contain personal information.

I first asked Codex for read-only analysis of the report model, service, tests, RLS verification script, migration strategy, and documentation. Codex identified that the UI did not need the fetched reporter UUID. It recommended an explicit seven-column projection, removal of `reporterId` from the public model, database column restrictions for both client roles, preservation of authenticated INSERT ownership, and corresponding tests/documentation. I approved that approach before asking Codex to implement it.
